## 1. Idea in one sentence

One command runs the Interstice app on the Vega Virtual Device through its use cases and produces a page that shows, for each acceptance criterion of the app, what was on screen, what the viewer was told, and the log lines that decided the result — including the criteria it cannot close, and why.

## 2. What we provide (our side)

| what | where |
|---|---|
| **The verification report** — a static page: a matrix of the app's criteria, one card per use case, and a list of what the report cannot show | `docs/e2e`, served by GitHub Pages (`C11`, `C22`) |
| **The run records behind it** — one JSON file per suite, the full trace of every scenario, the captures | `docs/e2e/run/` |
| **The harness** — the code that produced them, re-runnable | `e2e/` (`C1`–`C10`) |
| **Its own tests** — including a selftest that shows each scenario can fail | `e2e/__tests__/`, run by `npm test` |

**How to read a result.** Each carries three labels, and they are part of the data, not the styling:

- **The suite.** RELEASE ran against the unmodified Release package — the submitted binary. VARIANT ran against a test build, made from the same source with one build-time flag, that loads its content from the test host so that faults can be injected (`decisions.two_suites`).
- **FIXTURE.** A VARIANT result used a stand-in description track: declared cue windows, cue text reading "Fixture cue N", never packaged, never in the demo (`decisions.fixture_track`). It shows the app's scheduling, switching and failure handling. It does not show the product's descriptions, which are generated by the pipeline and are a separate deliverable.
- **The verdict**, one of four (`decisions.verdict_vocabulary`): pass, fail, blocked, skipped. **Blocked** means the scenario could not run and names what stands in the way; it is drawn as prominently as a failure.

**What decides a verdict.** Assertions over the app's own trace — the `INTERSTICE.*` lines it emits at every state change — and nothing else (`decisions.trace_is_the_oracle`). Screenshots and clips illustrate. A run whose trace has a gap in its sequence numbers fails, whatever its assertions said.

**How the app's 22 criteria are classed** (`limits.coverage`): 4 automated, 4 fixture, 1 blocked, 2 hardware, 2 manual, 9 out of scope — each number counts criteria of the app in that class. *Out of scope* means the criterion concerns the pipeline, the open-source package or the submission itself, where no device run can speak.

**What the report cannot show**, stated on the page itself:

- that a listener **hears** the film get quieter — the trace shows the volume property set to 25% and restored;
- **VoiceView** consuming the announcements — it cannot be enabled in the Virtual Device;
- the **memory bound on a physical Fire TV** — every run is on the Virtual Device;
- that a cue **avoids dialogue** — fixture windows are declared, not derived from subtitles.

## 4. Payload / interface you will receive (reference)

Copied from `_facts.yml contracts.*`.

**A run** — `docs/e2e/run/<suite>/run.json`, `contracts.run_record`:

| field | meaning |
|---|---|
| `run_id` | string |
| `started_at` | ISO 8601 string |
| `suite` | release \| variant |
| `conditions` | { target_platform, build, content_asset } |
| `app_commit` | string |
| `package_version` | string |
| `capture_rung` | grpc \| appium \| none |
| `input_route` | inputd-cli \| grpc |
| `selftest` | { ran: boolean, scenarios_that_can_fail: integer, of: integer } |
| `restored_release` | boolean \| null — after a VARIANT suite, whether the Release package was reinstalled and said e2e=false; null for a RELEASE suite |
| `results` | scenario_result[] |

**A result** — each entry of `results`, `contracts.scenario_result`:

| field | meaning |
|---|---|
| `id`, `name` | string |
| `suite` | release \| variant |
| `use_case` | string |
| `covers` | string[] — ids in the app acceptance list |
| `fixture` | boolean |
| `verdict` | pass \| fail \| blocked \| skipped |
| `reason` | string \| null — required unless pass |
| `blocked_by` | string \| null — required when blocked |
| `steps` | array of { at_ms, action, detail } |
| `assertions` | array of { kind, expect, ok, matched_seq } |
| `spoken` | string[] — what the app announced, in order |
| `artifacts` | array of { kind: screenshot \| clip, path, at_seq, caption } — path relative to the run directory |
| `trace_path` | string — relative to the run directory |
| `duration_ms` | integer |

**A trace line** — one JSON object per line of each trace file, `contracts.trace_event`:

```json
{
  "boot": "k3f9x2",
  "seq": 41,
  "t_dev_ms": 1791471731402,
  "t_host": "2026-10-08T15:02:11.482Z",
  "line": "INTERSTICE.audio.duck id=probe to_pct=25",
  "name": "audio.duck",
  "fields": { "id": "probe", "to_pct": "25" }
}
```

`boot` identifies one launch of the app; `seq` counts from 0 within it. `matched_seq` in an assertion points at the line that settled it.

## 5. Checklist for you (the reader who chooses to check)

Each item can be done from the published page and the repository, with no device.

- [ ] The matrix has one row per criterion in `docs/features/interstice/_facts.yml acceptance[]`. Count both.
- [ ] Pick any passing card. Its "decided by" lines appear, in that order, in the trace file it links to.
- [ ] Every VARIANT card says FIXTURE. No RELEASE card does.
- [ ] `S17` is present and blocked, and says why.
- [ ] The page lists what it cannot show, above the cards.
- [ ] `run.json` reports `selftest` with `scenarios_that_can_fail` equal to `of`.
- [ ] `run.json` of the VARIANT suite reports `restored_release: true`.
- [ ] `git log -- docs/e2e` dates the published run inside the submission window.

## 6. How we test it together

There is no joint step: nothing here needs two parties. A reader with the Vega SDK can reproduce the RELEASE suite alone, and that is the whole procedure:

1. Boot the Vega Virtual Device (SDK 0.24).
2. `npm ci`, then the RELEASE suite — `npm run e2e:release`.
3. Five verdicts print; the run record is written under `e2e/out/`. Compare it with `docs/e2e/run/release/run.json`: same scenarios, same verdicts, same decisive lines. Timings and the launch ids differ.

A reader without the SDK can run `npm run e2e:report`, which rebuilds the page from the committed run with no device (`AC11`), and `npm test`, which runs the harness's own tests including the selftest (`AC4`).

## 7. Questions to close

None are addressed to the panel. Two are open on our side and are stated here because a careful reader will reach them:

- **The app has no seek control** (`defects[D6]`). The criterion about seeking and held-key resync in the app's own list cannot be demonstrated on a device, by this harness or by hand, until one exists. The report shows that scenario as blocked rather than omitting it.
- **Every run is on the Virtual Device.** Three of the app's criteria close only on physical hardware; this harness does not change that and does not claim to.
